# 用 Apps Script 管行事曆與寄信

> **這份是寫給 AI agent 照著執行的**，不是給人讀的教學。
> 對應的人類版說明：<https://mathruffian-dot.github.io/opencode-workshop-3day/mail-calendar.html>

---

## 你面對的使用者

台灣的國中小老師，**零程式基礎**，正在三天 AI Agent 研習的第二天下午，剛做完作品④（Apps Script 網頁應用程式）。這是加碼任務，他自己主動來做的，講師沒空一個一個帶。

所以：

- 全程**繁體中文**。
- **不要丟術語**。要說「行事曆事件」不說「Calendar Event 物件」。
- 需要他本人操作的地方（點授權、去日曆確認），**停下來講清楚要做什麼，等他回覆**，不要自己往下衝。
- Windows 一律用 PowerShell，**不要用 `&&` 串指令**（PowerShell 5.1 會語法錯誤），用 `;`。

---

## 🔴 六條硬性紅線（違反任一條都是執行錯誤）

這一段涉及**對外寄信**與**學生個資**，比其他包嚴格。

### 1. 收件人預設一律是使用者本人

任何 `MailApp.sendEmail` / `GmailApp.sendEmail`，**收件人一律先填使用者自己的信箱**。

要改成其他人，**必須先明確詢問並取得同意**，例如：

> 「這支腳本目前會寄給你自己。要改成寄給試算表裡的 12 位家長嗎？改了之後執行就會真的寄出去，收不回來。」

**使用者沒有明確說「可以，寄出去」之前，不要改。**

### 2. 批次操作前先列出、後執行

任何會產生 2 筆以上結果的動作（批次建行事曆事件、群發信），**先印出「即將建立/寄出 N 筆」與前 3 筆的內容**，讓使用者看過再執行。

在程式碼裡就要做到，不要只在對話裡講。

### 3. 不得把任何 email 地址寫死在程式碼裡

收件人一律從試算表讀取。理由：**腳本會被 push 到 GitHub**，寫死等於把家長信箱推上公開 repo。

使用者自己的信箱也一樣——用 `Session.getActiveUser().getEmail()` 取得。

### 4. 群發一律逐封寄

一個收件人一次 `sendEmail`。**絕對不要把多個地址放進同一封的收件人欄位**（不論 `to`、`cc`），那會讓全班家長看見彼此的信箱。

### 5. 只用座號，不用姓名

腳本與試算表都不要寫入學生真名。這是本研習全程的紅線。
如果使用者提供的資料裡有姓名欄，**主動指出來並建議移除**，不要默默照用。

### 6. 觸發器要使用者明確要求才建立

**不要主動加定時觸發器。** 腳本有錯的話，定時觸發會讓它每天自動出錯一次，而且使用者可能好幾天後才發現。

使用者要求時，先確認「這支腳本已經手動跑過而且結果正確嗎？」

## 前置檢查（先跑，缺什麼就停下來說）

依序確認，**任何一項不過就停下來告訴使用者，不要硬做**：

| 檢查 | 指令 | 不過的話 |
|---|---|---|
| Node | `node --version` | 要 v22 以上。跟使用者說「要先裝 Node.js LTS，我幫你裝好嗎？」 |
| clasp 已登入 | `npx @google/clasp login --status` | 沒登入 → 引導他做 `npx @google/clasp login`，**提醒選個人 Gmail** |
| 有綁定的 Apps Script 專案 | 當前資料夾有 `.clasp.json` | 沒有 → 問他要接哪一份試算表，或是否要新建 |

> ⚠️ 如果 clasp 登入時出現 `admin_policy_enforced`，那是**學校 Google 帳號被管理員擋住**，使用者自己解不了。請他 `npx @google/clasp logout` 之後改用個人 Gmail。

## 任務一：行事曆（一定先做這個）

**順序不可調換。** 行事曆做錯只影響使用者自己、刪掉就好；寄信錯了是對外的，收不回來。先讓他在無風險的地方確認整條路是通的。

### 1-1 讀

加一個函式，讀出使用者本週的行事曆事件並印出來。

執行後**請使用者確認印出來的是不是他真的行程**。有印出來 = 授權與讀取都通了。

### 1-2 寫單筆

加一個函式，建立一個測試事件。

執行後**請使用者去 Google 日曆看一眼**事件有沒有出現。**等他回報再往下。**

### 1-3 批次（從試算表建）

讀試算表建立多筆事件。**套用紅線 2**：先印出「即將建立 N 筆」與前 3 筆內容。

> 時區：Apps Script 專案的時區若不是 `Asia/Taipei`，事件時間會差幾小時。建立批次事件前先確認 `appsscript.json` 的 `timeZone`。

---

## 任務二：寄信（行事曆全部正確才能開始）

### 2-1 寄給自己

收件人用 `Session.getActiveUser().getEmail()`。

⚠️ **第一次執行會跳「Google 尚未驗證這個應用程式」** —— 這是正常的，因為那就是使用者自己寫的腳本。**要主動先跟他說**，否則多數人會在這裡停手：

> 「等一下會跳一個紅色警告說『Google 尚未驗證這個應用程式』。那是正常的——因為那支腳本就是你自己寫的，本來就沒有送給 Google 驗證。請點左下角的『進階』，再點『前往〈你的專案名〉（不安全）』，然後允許。」

### 2-2 個人化內容

從試算表逐列讀取、逐封寄出。**收件人仍然全部填使用者自己**（紅線 1）。

請他確認收到的三封信：內容有沒有真的隨人不同。

### 2-3 換成真正的收件人

**這一步一定要先問過**（紅線 1）。得到明確同意後才改。

改完之後、執行之前，再印一次「即將寄給 N 位，第一位是 XXX」。

## 配額（要主動告知，不要等他撞牆）

| | 一般 Gmail | 學校 Workspace |
|---|---|---|
| 每天寄信對象 | **100** | 1,500 |
| 每天建行事曆事件 | 5,000 | 10,000 |

使用者要群發超過 80 封時，**主動提醒剩餘額度**。撞到上限會拋 `Service invoked too many times`，要等 24 小時。

---

## 錯誤處理

| 錯誤 | 意義 | 你要做的 |
|---|---|---|
| 授權畫面出現「Google 尚未驗證這個應用程式」 | 正常，自己的腳本沒送驗證 | 引導：進階 → 前往〈專案名〉（不安全）→ 允許 |
| `Service invoked too many times` | 配額用完 | 告知要等 24 小時，並說明一般帳號每天 100 封 |
| `You do not have permission to call MailApp.sendEmail` | 授權流程沒走完 | 請他重新執行一次，把授權走完 |
| 信寄出但內容空白 | 試算表欄位讀錯 | **先印出讀到的每一列**給使用者看，再往下 |
| 事件時間差幾小時 | 時區 | 檢查 `appsscript.json` 的 `timeZone` 是否為 `Asia/Taipei` |
| `admin_policy_enforced` | 學校帳號被管理員擋 | 請他改用個人 Gmail 重新登入 |

## 完成後回報

做完之後，用這個格式回報，**然後停下來**：

```
✅ 行事曆：可以讀、可以寫、可以從試算表批次建立
✅ 寄信：已寄 N 封測試信到你自己的信箱
⚠️ 收件人目前還是你自己 —— 要換成真正的收件人請告訴我
📊 今天已用掉 N/100 封額度

下一步建議：
- clasp push 把程式碼推上去
- 收工時跟主線一起 push 到 GitHub
```

**不要自作主張繼續做下一件事**（例如順手加觸發器、順手改收件人）。研習現場是跟著講師進度走的，你多做的每一步都是講師台上要收拾的狀況。

---

## 不要做的事

- ❌ 不要主動建立定時觸發器
- ❌ 不要在使用者沒明確同意前，把收件人改成他本人以外的地址
- ❌ 不要把 email 地址或學生姓名寫進程式碼
- ❌ 不要用 `GmailApp` 去讀取或刪除使用者的信件——本任務只需要「寄」，讀信不在範圍內，權限要求也高得多
- ❌ 不要建議使用者去 Google Cloud Console 申請 OAuth 用戶端。**這條路完全不需要那個**，那是另一條路（而且未驗證的應用 refresh token 7 天就失效）
